# Briefing S01-B08: the scenario editor, VIDEO and INTERACTIVE

Track: theserver, Season S01. Repo `github.com/cyb3rgun/theserver`, `main` at `3962388` or later. Implementer: CC. Architect: Mausi.

An operator with no programming knowledge sits in front of the admin page, uploads a video, sees a timeline, draws zones on a paused frame, moves them through time, gives them values and time windows, chooses reactions, previews the whole thing with the mouse as the pistol, and publishes. That is this pass. The editor works on a draft the server keeps; the server assembles the package, computes the `[files]` table, validates with `internal/scenario` and publishes through the existing chain. Nothing in the editor bypasses B07.

## 1. Decisions taken in this briefing, with reasons

- **Drafts live on the server, not in the browser.** A draft is a row in `scenario_drafts` (id, scenario_id, manifest as JSON, media dir, updated_at, updated_by) with its media under `content/drafts/<draft id>/media/`. Every editor action is a request that changes the draft and returns the changed fragment; closing the browser loses nothing. D-041.
- **The server assembles the package.** On publish the server writes `manifest.toml` from the draft, computes the `[files]` hashes, zips, runs `scenario.Validate`, and hands the result to the B07 store. The editor never sees a hash. D-042.
- **One vendored editor script, no framework.** The drawing canvas, the timeline and the video scrubber are one plain JavaScript file, embedded with an integrity hash like `settings.js`, talking to the draft endpoints. HTMX renders the forms around it. No bundler, no npm, no CDN. D-043.
- **Preview is the client's rule engine in the browser.** A small JavaScript implementation of section 7 of `docs/scenario.md` (appearances, zones, time windows, immediate and follow up reactions) runs the draft with the mouse as the pistol and shows score, hits, misses, timeouts. It is the same rule set theclient will implement in Go; both are checked against the same fixture in later passes. D-044.
- **Media stays as uploaded in S01.** No transcoding; the editor accepts the container and codec list from `docs/scenario.md` section 6 and rejects others at upload with a translated message. The browser must be able to play the file, which is the practical test. D-045.
- **Every editor field has label, hover description and why, in both languages,** rendered through the same mechanism as the settings page: a field registry for editor fields, so the editor and the settings share one help component. D-046.

## 2. Hard constraints

As in B01 to B07. The look is the founder's: the editor needs a clear structure (timeline left to right, canvas above, property panel beside, help everywhere) and nothing decorative. Keyboard shortcuts documented on the page.

## 3. Tasks

Commit: `fix(scenario): layer on layered appearances, openapi parse test`.

### Task 1: drafts

Migration 0007 `scenario_drafts`; `internal/content` draft directory handling; store functions create, get, list, update manifest JSON, delete, promote (publish). API: `POST /api/v1/drafts` (from scratch with id, tier, title; or from a published version as a copy), `GET /api/v1/drafts`, `GET /api/v1/drafts/{id}`, `PATCH /api/v1/drafts/{id}` (a JSON merge on the manifest with server side validation of the touched fields), `DELETE`, `POST /api/v1/drafts/{id}/media` (multipart, container and codec check per D-045, returns the media path and, for video, duration and dimensions probed by the browser and sent back in a second call), `DELETE /api/v1/drafts/{id}/media/{name}`, `POST /api/v1/drafts/{id}/validate` (returns problems), `POST /api/v1/drafts/{id}/publish` (assembles per D-042, returns problems or the new scenario version).

Tests: create, patch, media, validate with a known problem, publish yields a package identical in validation result to the B07 fixture chain, publish of a draft with problems refused.

Commit: `feat(drafts): server side scenario drafts with media, validation and publish`.

### Task 2: the editor page

`/admin/editor/{draft id}`:

- **Video area:** the main video (VIDEO) or the current media state clip (INTERACTIVE) in an HTML video element with a scrubber and frame stepping; a canvas overlay with the draft's zones at the current time.
- **Timeline:** scenario time left to right; appearances as bars (drag to move, drag ends to resize); keyframes of the selected zone as markers; a playhead; zoom.
- **Zones:** draw rect, circle, polygon on the paused frame; select, move, edit points; add a keyframe at the playhead from the current shape; delete keyframe; the shape between keyframes shown interpolated when scrubbing.
- **Property panel:** the selected object's fields (zone: name in both languages, class, points; appearance: start, end, zones, required hits, timeout behaviour, media state; reactions immediate and follow up; rules) as forms from the editor field registry with help.
- **Media panel:** upload, list, delete, assign to states (INTERACTIVE).
- **Validate** button showing translated problems that link to the object.
- **Publish** button, disabled while problems exist, that runs Task 1's publish and jumps to the B07 detail page.
- Autosave on every change through `PATCH`; an unsaved indicator only during a request.

All texts in both languages; the editor field registry has both languages for every field.

Tests: page renders for a draft; each draft endpoint is reachable from a page control (a test walks the rendered HTML for the expected data attributes); the integrity hash of `editor.js` matches; the language test covers the page.

Commit: `feat(admin): scenario editor for video and interactive`.

### Task 3: preview

`/admin/editor/{draft id}/preview`: full screen canvas over the video, the rule engine of D-044 in JavaScript, mouse click as a shot, a score panel with points, hits, misses, timeouts and lives, immediate reactions drawn on the canvas (flash, hitmarker), follow up clips switched for INTERACTIVE, a restart button. The engine is a separate file `rules.js` with its own tests run by a Go test through a JavaScript engine is out of scope; instead the engine's decisions for a fixture are recorded as a JSON trace and compared with a Go implementation of section 7 in `internal/scenario/rules.go` on the same fixture. That Go implementation is the seed for theclient.

Tests: Go rules on the INTERACTIVE fixture produce the expected trace; the JavaScript trace recorded in the browser proof equals it.

Commit: `feat(editor): preview with the section 7 rule engine in browser and in Go`.

## 4. Acceptance criteria

- A person can, in the browser and without touching a file, create a draft, upload a video, draw two zones with keyframes, add two appearances with time windows, set reactions and rules, preview with the mouse, validate, publish, and see the result in the B07 catalogue and on a simulated device.
- The published package validates identically whether it came from the editor or from a hand made zip.
- The Go rules and the browser rules produce the same trace on the fixture.
- Every field in the editor has both languages and help; no hard coded strings.
- One commit per task plus handover on `origin/main`.
