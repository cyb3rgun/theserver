# Briefing S01-B07: scenario packages and the catalogue

Track: theserver, Season S01. Repo `github.com/cyb3rgun/theserver`, `main` at `446941e` or later. Implementer: CC. Architect: Mausi.

`docs/scenario.md` (placed by the founder, uncommitted) is the reference for this pass and is committed in Task 1. This pass makes scenarios real on the server: a shared package that parses and validates a scenario, a content store that keeps every published version, upload and validation from the admin page, a catalogue with covers and tiers, a download endpoint for targets, and the device side reporting which versions it holds. The editor that draws zones on a timeline is B08 and stands on this.

## 1. Decisions taken in this briefing, with reasons

- **`internal/scenario` is the one implementation of `docs/scenario.md`.** Manifest types, TOML parsing, validation with typed, translatable errors (field, code), and package reading from a directory or a zip. theclient will import the same package later, so it must not depend on `store` or `httpapi`. D-035.
- **Content store on disk, index in SQLite.** Packages live under `Server.DataDir/content/<id>/<version>/` exactly as uploaded; the database holds `scenarios` (id, version, tier, title, age rating, manifest hash, size, uploaded_at, uploaded_by, status draft or published) and `device_scenarios` (device_id, scenario_id, version, installed_at, current). Media is never stored in the database. D-036.
- **Versions are immutable once published.** Uploading the same id again creates the next version; a published version is never overwritten or deleted in S01. Drafts may be replaced. D-037.
- **Targets fetch, the server never pushes media.** `GET /api/v1/scenarios/{id}/{version}/package.zip` with a device token, resumable (`Range`), with `X-Manifest-SHA256`. The link carries only the announcement command `content_available {id, version, sha256, size}` and the device reports its holdings. D-038.
- **Age rating is enforced at assignment.** A scenario rated 18 cannot be assigned to a session whose devices are marked for a younger room; S01 carries the field and the check, the room rating comes with rooms in a later pass, so for now the check compares against a device level `min_age` setting that defaults to 18. D-039.
- **Validation is bilingual through the settings foundation.** Every validation error has a code with `en` and `de` texts in the catalogues; the admin shows the translated text plus the detail line, per D-033 style. D-040.

## 2. Hard constraints

As in B01 to B06. Additionally: no media codec dependencies in this pass; the server validates presence and hashes of media files, not their content.

## 3. Tasks

Commit: `fix(admin): create the config file on first save, show error details`.

### Task 1: the scenario package

`internal/scenario`: `Manifest` types for every section of `docs/scenario.md` versions 1; `Load(dir)`, `LoadZip(path)`; `Validate(m, files) []Problem` where `Problem` is `{Field, Code, Detail}` and codes are constants (`missing_media`, `hash_mismatch`, `zone_without_appearance`, `appearance_unknown_zone`, `keyframes_unordered`, `tier_media_mismatch`, `no_canvas`, `no_age_rating`, `bad_shape`, `bad_time_window` and whatever else the document implies); `Hash(m)` over the manifest and the media hashes in a stable order. Commit `docs/scenario.md` in this task.

Tests: a valid VIDEO and a valid INTERACTIVE fixture under `testdata/`; one fixture per validation code that fails with exactly that code; hash stable across map ordering; zip and directory loads are equal.

Commit: `feat(scenario): manifest, validation and package loading`.

### Task 2: content store

`internal/store`: migration 0005 with `scenarios` and `device_scenarios`; functions `PutScenario`, `PublishScenario`, `ListScenarios`, `GetScenario(id, version)`, `LatestPublished(id)`, `RecordDeviceScenarios(deviceID, holdings)`, `DeviceScenarios(deviceID)`. `internal/content`: writes an upload to `content/<id>/<version>/` atomically (temp dir, rename), computes size and hash, refuses to overwrite a published version, serves file paths for download.

Tests: put then publish then put again yields version two; overwrite of published refused; atomic write leaves nothing behind on failure.

Commit: `feat(content): scenario store with immutable published versions`.

### Task 3: protocol and link

`docs/protocol.md` section 8 gains: the `health` event carries `scn` as a list of `{id, ver}` the device holds; a new command `content_available {id, ver, sha, size}`; a new event kind `content` with `{id, ver, st}` where `st` is `installing`, `installed`, `failed`, `removed`. Sections 1 to 7 untouched. The link records holdings from `health` and `content` events into `device_scenarios`. `simtarget` reports a configurable holdings list and answers `content_available` by downloading the package over HTTPS with its device token, verifying the hash, and sending `content installed`.

Tests: link records holdings; simulator end to end downloads a fixture package and reports installed; hash mismatch reports failed.

Commit: `feat(link): scenario holdings and content announcements`.

### Task 4: API

- `GET /api/v1/scenarios` (list with latest published and drafts), `GET /api/v1/scenarios/{id}`, `POST /api/v1/scenarios` (multipart zip upload, validates, stores as draft, returns problems if any), `POST /api/v1/scenarios/{id}/{version}/publish`, `DELETE /api/v1/scenarios/{id}/{version}` (drafts only)
- `GET /api/v1/scenarios/{id}/{version}/package.zip` for devices (device token) and admins, with `Range` support and the hash header
- `POST /api/v1/sessions/{id}/scenario` with `{id, version}`: assigns, checks the age rating against the session's devices (D-039), sends `content_available` to every device of the session that does not hold that version
- `GET /api/v1/devices/{id}/scenarios`
- New setting `Content.MaxUploadMB` (default 2048) and `Content.Dir` (default `<data>/content`), through the registry with both texts
- OpenAPI and the coverage test.

Commit: `feat(api): scenarios, upload, publish, package download and session assignment`.

### Task 5: admin catalogue

- `/admin/scenarios`: the catalogue as cards or rows (structure only, look is the founder's): cover, title in the admin language, tier, latest published version, drafts, age rating, size; upload control with progress; per scenario a detail page with versions, the validation result of a draft (translated code plus detail), publish and delete for drafts, and which devices hold which version.
- `/admin/sessions`: choose a scenario and version for a session; age rating conflicts shown as a translated error.
- `/admin/devices`: the detail shows held scenario versions and whether the current one is installed.
- Catalogue entries in `en` and `de` for everything above.

Tests: upload of the VIDEO fixture appears in the catalogue as a draft with no problems; upload of a broken fixture shows the translated problem; publish then assign to a session sends the announcement to a connected simulator (end to end).

Commit: `feat(admin): scenario catalogue, upload, publish and assignment`.

## 4. Acceptance criteria

- `docs/scenario.md` is committed and `internal/scenario` implements it with a fixture per validation code.
- Upload, validate, publish, assign, announce, download, verify, report installed: the whole chain runs end to end with the simulator, and the admin shows every step.
- Published versions cannot be changed or deleted.
- Every new text exists in both languages; every new setting is in the registry.
- One commit per task plus handover on `origin/main`.
