# Briefing S01-B12: target types

Track: theserver, Season S01. Repo `github.com/cyb3rgun/theserver`, `main` at `26da418` or later. Implementer: CC. Architect: Mausi.

A target type describes a kind of target once, so that devices, scenarios and clients stop carrying the same numbers by hand: the display, its resolution and orientation, where the beacons sit in centimetres relative to the picture, the class, the sound. Devices belong to a type; a scenario is made for a type (its canvas); a client gets its calibration from the type. The first three types are real: the 10.1 inch board, the 11.9 inch bar display (1480 x 320, HDMI) and a 50 inch television. The phone stand and the mannequin follow as data, not code.

## 1. Decisions

- **A target type is data, editable in the admin, never in code.** Table `target_types`: id, name (en, de), class (esp, pi, pc), display width and height in mm, resolution width and height in px, orientation (landscape, portrait), beacon layout as a list of clusters with x and y in mm relative to the picture's top left corner (negative values allowed, a cluster may sit outside the picture), sound (none, builtin, hdmi, usb), notes (en, de), created and updated. D-061.
- **Canvas follows the type.** A type's canvas is its resolution and orientation; the editor offers the canvas of a chosen type when a draft is created, and a scenario records `target_type` in its manifest section `[display]` as an optional field, validated when present. A scenario without a type keeps its own canvas as before. D-062.
- **Calibration is derived, not typed.** From the beacon layout and the picture size the server computes the beacon rectangle in canvas coordinates and sends it to the device as `set_config` with key `calib.rect` on approval, on type change and on connect. theclient's `Calib.Rect` setting stays as the manual override. Protocol section 8 records the key and its value shape. D-063.
- **Three seed types ship with the migration**, marked `builtin`, editable but not deletable: `board-10` (10.1 inch, 1280 x 800, landscape, four clusters at the picture edge midpoints), `bar-12` (11.9 inch, 1480 x 320, landscape, four clusters at the corners of a 350 x 200 mm frame around the picture) and `tv-50` (50 inch, 1920 x 1080, landscape, four clusters at the edge midpoints). Numbers as given here, corrected by the founder in the admin later. D-064.
- **The devices page shows the type and lets the operator assign it**; the type page draws the beacon layout as a simple outline picture (picture rectangle plus cluster dots, structure only) so the operator sees what the numbers mean. D-065.

## 2. Tasks

1. `feat(store)`: migration 0008 `target_types` with the three seeds, `devices.target_type` (nullable), functions to list, get, create, update, delete (refused for builtin or when devices use it).
2. `feat(api)`: `GET /api/v1/target-types`, `GET .../{id}`, `POST`, `PUT .../{id}`, `DELETE .../{id}`, `POST /api/v1/devices/{id}/target-type` with the calibration push per D-063; `GET /api/v1/target-types/{id}/calibration` returns the derived rectangle; OpenAPI; tests including the derivation for the three seeds with hand computed expected values.
3. `feat(admin)`: `/admin/target-types` list and detail with the outline picture, create and edit forms through the field registry with help in both languages; type selector on the device page; the editor's new draft dialog offers "canvas from type".
4. `feat(scenario)`: optional `[display].target_type` in `pkg/scenario`, validated against the existing types at upload; the editor writes it when a type was chosen.
5. `docs`: `docs/scenario.md` amended (section 2, optional field, dated), `docs/protocol.md` section 8 (`calib.rect`), D-061 to D-065, `docs/settings.md` if settings changed, README, seasons, briefing; handover; push; tag `v0.4.0`.

## 3. Acceptance

The three seed types exist after migration; a device assigned to `bar-12` receives `calib.rect` on connect and the simulator logs it; a draft created "from type bar-12" has canvas 1480 x 320; deleting a builtin or used type is refused with a translated message; the outline picture renders for each seed; all texts in both languages.
