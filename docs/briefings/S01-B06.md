# Briefing S01-B06: the settings foundation

Track: theserver, Season S01. Repo `github.com/cyb3rgun/theserver`, `main` at `4d36bf1` or later. Implementer: CC. Architect: Mausi.

The admin interface is the product. Operators have no programming knowledge; they must see, understand and change every setting themselves, with an explanation next to it. This pass builds the machine that every later admin page and editor is made with: one registry that describes every setting once, and renders it as a form with help, validation and two languages. Configuration becomes editable from the admin page. No scenario editor yet; that stands on this.

## 1. Decisions taken in this briefing, with reasons

- **One settings registry, defined in code, rendered everywhere.** `internal/settings` declares every setting once: key, type, default, unit, range or allowed values, section, whether a change needs a restart, and texts in English and German (label, description, why). The config loader, the default file writer, the API and the admin form all read the registry; nothing describes a setting twice. D-030.
- **Two languages from the first form.** `internal/i18n` with embedded catalogues `en` and `de` as TOML; every admin string and every settings text goes through it. Language per admin session (cookie), default from `Admin.Language`, fallback English. A test fails when any key is missing in either language. D-031.
- **Settings are written back to the TOML file the server was started with.** The admin page writes the file, keeps comments and order by regenerating it from the registry, and marks values that need a restart. Values that can be applied live (log level, link timings) are applied live. D-032.
- **Every change is logged with who, when, key, old value, new value** as a structured log line now; the audit table comes with roles in a later pass and will read the same event. D-033.
- **Help is part of the structure, not the design.** Every field renders label, unit, current value, default, a short description visible on hover and an expandable "why" with the longer text. How it looks is the founder's; that it exists is this pass. D-034.

## 2. Hard constraints

As in B01 to B05: no em dashes, no invented versions, Conventional Commits by module, English only in code and docs, help texts in both languages, nothing outside the repo, `tools/check_dashes.py` before every commit, one commit per task plus the handover commit, push at the end. The dash check must also pass on the German catalogue; German uses ASCII apostrophes and hyphens, umlauts are allowed.

## 3. Tasks

### Task 1: the registry

`internal/settings`:

```go
type Kind int // String, Int, Bool, Duration, Enum, Path, Addr

type Setting struct {
    Key          string   // "server.listen_addr"
    Section      string   // "server"
    Kind         Kind
    Default      any
    Unit         string   // "ms", "s", "MB", "" ...
    Min, Max     *int64   // for Int and Duration
    Enum         []string // for Enum
    Restart      bool     // change needs a restart
    Sensitive    bool     // never shown in logs or exports (none yet, reserved)
    Text         map[string]Text // "en", "de"
}

type Text struct{ Label, Description, Why string }
```

`All() []Setting` in a stable order, `Get(key)`, `Validate(key, value) error` with typed errors (out of range, not allowed, bad address, bad duration). Every existing setting from `internal/config` is declared here with both texts. The config struct is generated from the registry at load time or checked against it by a test that fails when a config field has no registry entry or a registry entry has no config field.

Tests: order stable, every setting has `en` and `de` with all three texts, validation cases per kind.

Commit: `feat(settings): registry with types, ranges, restart flags and bilingual texts`.

### Task 2: i18n

`internal/i18n`: embedded `catalog/en.toml` and `catalog/de.toml`, flat keys (`admin.devices.title`), `T(lang, key, args...)`, fallback to `en`, missing key renders the key itself in tests and logs a warning at runtime. Language resolution: session cookie, else `Admin.Language`, else `en`. A test walks both catalogues and fails on any key missing on either side. All existing admin template strings move into the catalogues.

Commit: `feat(i18n): english and german catalogues for the admin interface`.

### Task 3: config through the registry

`internal/config` loads defaults from the registry, keeps file, environment and flag precedence, and gains:

- `Sources()` already exists; extend to report the file path in use.
- `Write(path, values)` that regenerates the TOML file from the registry with comments (label and description in the file's language, `en` for the file), preserving unknown sections it did not create.
- `Apply(changes) (needsRestart []string, applied []string, err error)` that validates through the registry, applies live values (log level, link timings, admin language) and lists the keys that need a restart.
- New settings: `Admin.Language` (enum `en`, `de`, default `en`), `Admin.SessionHours` (default 12).

Tests: write then load round trip is identical; a live change takes effect; a restart change is reported and not applied; an invalid value is rejected with the typed error.

Commit: `feat(config): registry driven defaults, write back and live apply`.

### Task 4: API

- `GET /api/v1/settings` returns, per setting, key, section, kind, value, default, source, unit, range or enum, restart flag and the texts for the requested language (`?lang=`), plus a `restart_pending` list.
- `PUT /api/v1/settings` with `{key: value, ...}`: validates all, applies all or nothing, writes the file, logs each change (D-033), returns applied and restart pending.
- `POST /api/v1/settings/reset` with `{keys: [...]}` sets the defaults.
- OpenAPI updated; the route coverage test must stay green.

Commit: `feat(api): read, write and reset settings`.

### Task 5: admin settings page

`/admin/settings` becomes an editable form rendered from the registry: sections as groups, each field with label, control matching the kind (text, number with unit, switch, select), current value, default, source, a hover description, an expandable why, a per field reset, a save bar with the number of unsaved changes, and a banner listing keys that need a restart after saving. Language switch in the page header (writes the session cookie). Validation errors shown next to the field, in the chosen language, from the API's typed errors.

Tests: the page renders every registry setting; a save through the page changes the file; a restart banner appears for a restart key; the language switch changes the rendered labels.

Commit: `feat(admin): editable settings page from the registry with help and languages`.

### Task 6: docs and handover

- `docs/decisions.md`: D-030 to D-034.
- `docs/settings.md`: generated by a `theserver settings doc` subcommand from the registry, a table of every setting with default, unit, range, restart flag and the English texts; a test fails when the committed file is stale.
- `docs/openapi.yaml` updated; README settings section updated.
- `docs/briefings/S01-B06.md` verbatim.

Then `docs/handovers/S01-B06.md`, commit `docs(handover): add S01-B06 handover`, push.

## 4. Acceptance criteria

- Every setting exists exactly once, in the registry, with English and German texts, and the config, the default file, the API and the page all come from it.
- A setting changed on the page is in the file after save, live where possible, marked for restart otherwise, and logged with old and new value.
- Switching the language changes every visible string on the settings page; no hard coded admin strings remain.
- `docs/settings.md` is generated and current.
- One commit per task plus handover on `origin/main`.

## 5. Report back

`git log --oneline origin/main`, the number of settings in the registry, screenshots of the settings page in both languages with one hover and one expanded why, the log line of one change, and anything odd. A gap is a question, never a substitution.
