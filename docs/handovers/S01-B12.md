# S01-B12 handover

What the next session needs to continue without reading the log. A kind of target is data now. The table `target_types` describes one kind once: the picture in millimetres, the resolution in pixels, how it hangs, where the beacon clusters sit relative to the picture, the class of the computer and where the sound comes from; it is edited in the admin and never in code (D-061). The migration seeds the three types that exist today, marked builtin, which can be edited but not deleted (D-064). A device belongs to a type, and theserver derives the beacon rectangle from the type and sends it as `set_config` with the key `calib.rect`, on approval, on a type change and after every handshake (D-063). A scenario can name the type it was made for in `[display].target_type` and takes its canvas from it (D-062). The pages list the types, draw the layout as an outline and let a device be set to a type (D-065). The close of the pass is tagged `v0.4.0`. `go vet ./...` and `go test ./...` are green on go1.27.1 in 17 packages with 442 test functions.

## Read this first

- **The migration is 0010, not 0008.** The briefing says 0008; 0008 and 0009 were taken by the draft locks and the draft history of B09. It creates `target_types`, adds `devices.target_type` with its index and inserts the three seeds.
- **The rectangle is computed, never stored.** `store.TargetType.Calibration()` is a pure function: a millimetre is `res/display` pixels, the rectangle is the bounding box of the clusters, and the four corners come out in the order top left, top right, bottom right, bottom left. `Calibration.Value()` writes them as `"x,y x,y x,y x,y"`, which is exactly what theclient's `calib.rect` setting reads (its D-012). Changing the order or the rounding changes what every target does with a shot.
- **The seed numbers are partly computed.** The briefing gives diagonals and resolutions; the picture sizes were derived from the diagonal and the aspect ratio and rounded: 217 x 136, 295 x 64, 1107 x 623 mm. The class and the sound of each seed were chosen the obvious way. All of it is meant to be corrected in the admin, which is why nothing in the code depends on the values.
- **Three paths send the calibration, one function does it.** `link.Server.SendCalibration` reads the device, its type and the rectangle and sends the command; the API calls it after an approval and after a type change, the connection calls it in `calibrationOnConnect` before the session start. A device without a type is told nothing and that is not an error.
- **The admin form is a registry.** `internal/targettype` holds label, description and why per field in both languages, the same shape as `internal/settings` and `internal/editor`; the pages render all three with the `help` fragment. A new field belongs there first.
- **The beacon table needs no script.** The form renders one row per cluster plus an empty one: a row that is emptied is dropped, a row that is filled is added. `targetTypeForm` parses `beacon.x` and `beacon.y` as parallel lists.
- **The outline is structure.** `outlineOf` writes millimetres into an SVG viewBox with a margin; no text, no colour of its own, `currentColor` only. It is there so an operator sees what the numbers mean, not to look good.

## Traps that survived

- **A number input shows the decimal separator of the browser.** On a German system the form shows `-27,5` for `-27.5`; the browser sends the canonical form back. A value typed with a comma that the browser does not convert is refused with the translated message that asks for a dot.
- **Deleting a type is refused by the store, not by the database.** The foreign key would also refuse it, but the store checks first so the message can say which devices hold it.
- **`builtin` is never taken from a body or a form.** Only the migration writes it; a create that sends `"builtin": true` gets a type that is not builtin.
- **The shared field fragment lives in `fragments.html`.** Both target type pages parse layout, fragments and their own file only, so a define that two pages need belongs there.
- **The language cookie is HttpOnly.** A proof script cannot set it with `document.cookie`; it has to use the switch of the page, as `dist/proof10/script.json` does.

## Not done, open

- The phone stand and the mannequin are not seeded; they are data an operator writes when the hardware exists.
- Nothing compares the class a device reports with the class of its type, and nothing warns when a scenario made for one type is played on another. Both are checks a later pass can add now that the data exists.
- The orientation of a type is recorded and shown but changes nothing: the canvas is the resolution as it stands.
- A type that is deleted leaves the scenarios that name it untouched; they carry an id that no longer resolves, and only the next upload of that package says so.
- Everything B11 left open stays open: one start per device, no retry of a refused start, readiness on load and not live, and the older open points of B09 and B10.
